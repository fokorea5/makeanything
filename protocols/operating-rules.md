# 운영 규칙 (Operating Protocol)

## 규칙 1: 제작자 중심 컨트롤

모든 주요 단계가 끝나면 반드시 **[제작자 보고 및 승인 요청]** 양식으로 보고하고,
**승인을 얻어야만** 다음 단계로 진행할 수 있습니다.

> **쉬운 비유:** 요리사가 새로운 메뉴를 개발할 때,
> 사장님이 맛을 보고 "OK" 해야 메뉴판에 올리는 것과 같습니다.

### 세부 규칙
- 승인 없이 다음 단계 진행 **절대 금지**
- 긴급 상황에서도 최소한 사후 보고 필수
- 제작자가 "이건 아닌 것 같다"고 하면 즉시 방향 전환

---

## 규칙 2: 의도 누락 방지

**[의도 매칭 분석가]**는 개발 완료 후, 정찬님의 최초 요구사항과 결과물을 대조하여
누락된 기능이 있다면 **즉시 개발자에게 수정을 지시**합니다.

### 세부 규칙
- 프로젝트 시작 시 모든 요구사항을 번호 매겨 기록
- 매 단계 완료 시 요구사항 체크리스트 업데이트
- 최종 검수 시 100% 매칭 확인 필수

---

## 규칙 3: 경제성 우선

**[경제성 & 법률 검수관]**은 API 호출 비용을 최소화하는 최적화 방안을 **항상** 제시해야 합니다.

### 세부 규칙
- 모든 외부 API 사용 시 비용 추정 필수
- 더 저렴한 대안이 있으면 반드시 제시
- 월간 예상 운영비 보고

---

## 규칙 4: 계층적 대화

복잡성을 줄이기 위해, **현재 단계에 필요한 에이전트들만** 대화에 참여하며,
**총괄 감독이 이를 중재**합니다.

### 단계별 참여 에이전트

| 단계 | 참여 에이전트 |
|------|--------------|
| 기획 | 총괄 감독, 경제성 검수관, 외부 정보 첩보관 |
| 설계 | 총괄 감독, 기술 아키텍트, 인터페이스 디자이너, 보안 QA |
| 개발 | 총괄 감독, 리드 개발자, 기술 아키텍트 |
| 테스트 | 총괄 감독, 보안 QA, 의도 매칭 분석가 |
| 배포 | 총괄 감독, 배포 전문가, 보안 QA |
| 수익화 | 총괄 감독, 수익화 설계자, 경제성 검수관 |

---

## 규칙 5: 비상 프로토콜

### 기술적 문제 발생 시
1. 리드 개발자가 문제 파악 → 기술 아키텍트와 협의
2. 해결 불가 시 총괄 감독에게 보고
3. 총괄 감독이 제작자에게 상황 보고 및 대안 제시

### 일정 지연 시
1. 해당 에이전트가 총괄 감독에게 즉시 보고
2. 총괄 감독이 일정 재조정 후 제작자에게 보고
3. 제작자 승인 후 조정된 일정으로 진행
